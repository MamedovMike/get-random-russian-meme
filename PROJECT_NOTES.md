# Get Random Russian Meme — конспект проекта

## Идея

Pet-проект без цели охватить широкую аудиторию — для тех, кто ценит мемы
и хочет делиться ими. Открытая, пополняемая сообществом коллекция русских
мемов с простой модерацией через Telegram-бота. В интернете есть похожие
вещи (Know Your Meme, mem-hub.ru, fandom.wiki), но ни одна не закрывает
именно эту нишу: открытый, пополняемый через модерацию, чисто русский,
без категорий/тегов/видео — только рандомная выдача картинок.

## Принцип разработки

Не усложнять раньше времени. Сначала доказать, что работает базовая
концепция (один бот + одна таблица), и только потом добавлять новые слои
(API, users-таблица, дедупликация, хостинг) — по мере реальной необходимости,
а не заранее. Уже был случай, когда это правило нарушили (см. "Почему один
бот, а не два" ниже) — хороший пример, почему стоит его придерживаться.

## MVP scope

1. БД с фотографиями мемов (на деле — БД с `file_id`, не с самими файлами)
2. Приём мема от юзера → `pending` → модерация (одобрение/отклонение) →
   `approved`/`rejected`
3. Раздача случайного одобренного мема по запросу

Без тегов, категорий, гифок, видео — только статичные картинки, только рандом.

## Как хранятся фото

Файлы **не хранятся** ни в БД, ни на диске. Используется `file_id` —
идентификатор, который Telegram выдаёт при получении фото. По этому id
файл можно переслать в любой чат **тем же самым ботом** без повторной
загрузки. В БД лежит только текстовая строка.

Важно: `file_id` привязан к конкретному боту и не передаётся между разными
ботами (см. "Почему один бот, а не два" — это ограничение платформы и есть
причина текущей архитектуры).

## Схема БД (SQLite, локально)

Одна таблица, без отдельной таблицы `users` — она не нужна для MVP.

```sql
CREATE TABLE IF NOT EXISTS russian_memes (
    id INTEGER PRIMARY KEY,
    file_id TEXT NOT NULL UNIQUE,
    added_by BIGINT,
    status TEXT NOT NULL DEFAULT 'pending',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
)
```

Зачем поле `added_by`, если слать мем может кто угодно:
- антиспам (лимит N мемов в день с одного `telegram_id`)
- возможность одной командой почистить весь мусор от конкретного юзера
- задел на будущее (топ активных, статистика) без миграции схемы

`file_id UNIQUE` — защита от точных дублей на уровне БД.
`status DEFAULT 'pending'` и `created_at DEFAULT CURRENT_TIMESTAMP` —
не нужно прописывать вручную при каждой вставке. `id INTEGER PRIMARY KEY`
в SQLite уже ведёт себя как автоинкремент сам по себе — отдельное ключевое
слово `AUTOINCREMENT` не нужно (в SQLite оно означает не то же самое, что
в MySQL/Postgres, и просто не критично для MVP).

`init_db.py` — готов, финальная версия зафиксирована выше. Запускается
один раз, создаёт файл `russian_memes.db` рядом со скриптом.

⚠️ В `russian_memes.db` может физически присутствовать неиспользуемая
колонка `photo_path` — осталась от эксперимента с двумя ботами (см. ниже).
Не используется в текущем коде, можно игнорировать или почистить схему
отдельным шагом.

## Архитектура — один бот, код разнесён по модулям

Один процесс, один токен (`BOT_TOKEN`), напрямую работает с
`russian_memes.db` через `sqlite3`. Без отдельного API-слоя на старте —
лишняя сложность, пока бот живёт на одной машине. API имеет смысл добавить
позже, когда появится что-то ещё, что должно ходить в БД (веб-морда,
мобильное приложение).

Изначально всё лежало в одном файле (`getRRMBot.py`), потом код разнесён
по модулям ради читаемости (рефакторинг, поведение бота не изменилось):

- `bot_instance.py` — создание `bot` (`telebot.TeleBot`), чтение
  `BOT_TOKEN`/`MODERATOR_ID` из `.env`. Ни один другой модуль не создаёт
  свой `bot` — все импортируют этот.
- `db.py` — вся работа с SQLite (весь `sqlite3.connect`/`execute` живёт
  только здесь). Хендлеры вызывают функции по имени, не знают про SQL.
- `handlers_user.py` — пользовательские хендлеры.
- `handlers_moderation.py` — модераторские хендлеры.
- `getRRMBot.py` — точка входа: импортирует `bot` и оба модуля с
  хендлерами (импорт нужен ради побочного эффекта регистрации
  `@bot.message_handler`/`@bot.callback_query_handler`), в конце
  `bot.polling(...)`.

### Пользовательская часть (`handlers_user.py`)

- `/start` — приветствие + inline-кнопки "Получить рандомный мем" /
  "Отправить мем" ✅
- `callback_query_handler('getMeme')` → `SELECT file_id FROM russian_memes
  WHERE status='approved' ORDER BY RANDOM() LIMIT 1`, отправить через
  `bot.send_photo`; если пусто — сообщение "база пустая" ✅
- `callback_query_handler('sendMeme')` → просит прислать фото ✅
- `message_handler(content_types=['photo'])` → `INSERT` со
  `status='pending'` (по умолчанию из схемы). Ловит `sqlite3.IntegrityError`
  от `file_id UNIQUE` (повторная отправка того же файла/форвард) — вместо
  падения бот отвечает "уже отправляли этот мем" ✅

**UX-эксперимент и откат:** пробовали убирать inline-кнопки
(`edit_message_reply_markup(..., reply_markup=None)`) сразу после нажатия
— и у пользователя, и у модератора. По ощущениям после теста выглядело
нелепо (особенно для повторяемого действия вроде "Получить рандомный
мем" — пришлось бы каждый раз заново вызывать `/start`). Откатили,
кнопки остаются после нажатия. Альтернатива на будущее — reply-клавиатура
снизу экрана (как в @SuaiBot) вместо inline-кнопок, см. "Дальнейшие шаги".

### Модераторская часть (`handlers_moderation.py`)

Доступна только тебе — каждый хендлер начинается с проверки
`if message.from_user.id != moderator_id: return`. `moderator_id` — твой
личный `telegram_id`, хранится в `.env` как `MODERATOR_ID`. Обычные
пользователи не видят и не могут вызвать эти команды.

Модерация — пакетная (batch review), без кнопок под каждым мемом (подход
"А", подробности выбора — см. ниже):

- `/pending` → достаёт все записи со `status='pending'`, для каждой
  отправляет отдельным сообщением фото (по `file_id`) с подписью-номером
  (`caption=id`), без кнопок ✅
- `/reject <id1> <id2> ...` → парсит текст команды, отклонённые id
  переводит в `status='rejected'` (`WHERE id IN (...) AND
  status='pending'` — не трогает уже обработанные записи), отвечает
  списком отклонённых id и количеством оставшихся на модерации.
  Валидирует пустой ввод и нечисловые id, не падает ✅
- `/approve_all` → `UPDATE status='approved' WHERE status='pending'`,
  одобряет всё оставшееся одним запросом ✅

Старые кнопочные хендлеры (`approved_<id>`/`rejected_<id>` callback'и)
удалены как мёртвый код после перехода на эту схему.

Протестировано end-to-end: отправка мема → `/pending` → `/reject` →
`/approve_all` → одобренный мем отдаётся через "Получить Мем". Повторная
отправка того же мема не роняет бота. Работает.

### Валидация пользовательского ввода

- **SQL-инъекции** — везде параметризованные запросы (`?` + `execute(query,
  params)`), включая динамически собранный `IN (...)` в `/reject`.
- **Файлы кроме jpg/png, zip-бомбы** — закрыто архитектурой, а не
  дополнительным кодом: хендлер подписан на `content_types=['photo']`,
  значит через него проходит только то, что сам Telegram классифицировал
  как фото (уже сжатое им же); всё остальное (документы, архивы) в бот
  просто не попадает — обработчика для них нет. Содержимое файла бот
  никогда не скачивает и не распаковывает (хранит только `file_id`),
  поэтому zip-бомба физически не может сработать.

### Почему один бот, а не два

Изначально закладывались два отдельных бота (два токена, два процесса) —
пользовательский и модерация, оба читают общий файл БД. При реализации
столкнулись с ограничением платформы: **`file_id` уникален для каждого
бота и не передаётся другому боту** (официальная документация:
https://core.telegram.org/bots/api#file). Второй бот не мог отправить
модератору фото по `file_id`, сохранённому первым ботом — Telegram отвечал
`400: wrong file identifier`.

Пробовали обходной путь — первый бот реально скачивает и сохраняет файл на
диск (`bot.get_file` + `bot.download_file`), второй читает с диска вместо
`file_id`. Технически заработало, но добавило заметный вес: скачивание,
локальное хранение (отменяет более раннее решение "файлы не хранятся"),
чистка файлов после модерации, лишняя колонка в схеме.

После тестирования и рефлексии решили вернуться к одному боту:
- изначальное возражение ("не хочу видеть модераторские кнопки в личном
  боте") решается проверкой `moderator_id`, а не отдельным процессом
- ни одна из запланированных будущих фич (гифки/видео/музыка, категории,
  рейтинг, мобильное приложение) не завязана на количество ботов — это
  либо вопрос схемы БД, либо будущего API-слоя
- цена (лишний код скачивания/хранения файлов) не оправдана экономией

## Уведомление пользователя о статусе его мема — решено НЕ делать (пока)

Обсуждали вариант, чтобы после модерации пользователь узнавал, приняли
его мем или отклонили. Уперлись в то, что бот не может написать
пользователю, который его не запускал (Telegram `Forbidden`) — но при
одном боте это не проблема, юзер и так уже его запустил. Вопрос в другом:
возник более фундаментальный вопрос — а действительно ли пользователю
важно знать статус своего мема, если в проекте нет профиля/рейтинга?
Уведомление может стать осмысленным, когда появится фича рейтинга активных
публикующих юзеров (см. "Дальнейшие шаги") — тогда статус мема будет
влиять на что-то видимое пользователю, а не будет висеть в вакууме.
До этого момента — не усложнять.

Если/когда решим делать — вариант через pull, не push: команда вроде
`/mystats`, показывающая юзеру сводку по его `added_by`, а не бот,
пишущий первым.

## Первая волна улучшений MVP (20.08.2026) — реализовано

Цель волны — довести бота до состояния, пригодного для реального прод-
запуска: удобный UX, антиспам, косметика, деплой. Все пункты ниже
сделаны и протестированы (код — вручную через Telegram, Docker-сборка —
через реальный запуск контейнера).

**Reply-клавиатура снизу экрана** (взамен отменённого ранее UX-
эксперимента с удалением inline-кнопок, см. "UX-эксперимент и откат"
выше) — как в @SuaiBot. `handlers_user.py`: `ReplyKeyboardMarkup` с
кнопками "Получить Мем"/"Отправить Мем" создаётся один раз на уровне
модуля, хендлеры на неё — `message_handler` по совпадению `message.text`
(не `callback_query`, в отличие от inline). Старые `callback_query_handler`
для `getMeme`/`sendMeme` удалены как мёртвый код.

**Меню команд слева от поля ввода** — `bot.set_my_commands([...])` в
`getRRMBot.py`, вызывается один раз при старте. Команды: `/start`,
`/about`, `/help`, `/feedback`.

**Новый модуль `handlers_info.py`** — сервисные команды, не относящиеся
ни к работе с мемами (`handlers_user.py`), ни к модерации
(`handlers_moderation.py`):
- `/help` — как пользоваться ботом технически.
- `/about` — история и идея проекта, с HTML-разметкой
  (`parse_mode='HTML'`, `<b><u>...</u></b>` для акцента на "Русские Мемы").
- `/feedback <текст>` — приём багов/идей от любого пользователя. Реализовано
  как команда-с-аргументом (`message.text.split(maxsplit=1)`), без FSM/
  состояния — осознанно выбранный простой вариант (вариант "мгновенная
  пересылка модератору" вместо хранения в отдельной таблице БД). При
  вызове без текста — подсказка с примером синтаксиса, ничего не
  пересылается. При наличии текста — `bot.send_message(moderator_id, ...)`
  с `id` отправителя, плюс подтверждение самому пользователю.

**Лимит 20 мемов в день на пользователя** — `db.py`:
`count_user_memes_today(user_id)`, `SELECT COUNT(*) ... WHERE added_by=?
AND date(created_at) = date('now')`. Проверка в `sendMeme`
(`handlers_user.py`) до вставки; при `>= 20` — отказ без записи в БД.
Важный нюанс: "сутки" считаются по UTC (`CURRENT_TIMESTAMP`/`date('now')`
в SQLite — UTC), не по МСК — обнуление лимита происходит в 00:00 UTC
(03:00 МСК), не в полночь по ощущениям пользователя. Лимит считает все
статусы (`pending`/`approved`/`rejected`) за день, не только успешные —
иначе лимит обходился бы через намеренное попадание на отклонение.

**Известное и осознанно принятое ограничение** — если пользователь
шлёт несколько фото одним альбомом (media group), бот отвечает
отдельным подтверждением на каждое фото (Telegram не группирует альбом
в один апдейт, у каждого фото свой вызов хендлера, а явного сигнала
"это последнее фото группы" API не даёт). Функционально не баг — каждый
мем сохраняется корректно, просто шумно в чате. Правильное решение
(буферизация по `media_group_id` с таймером) — заметный слой сложности,
осознанно отложено, см. "Дальнейшие шаги".

**Docker-деплой** — `Dockerfile` (`python:3.13-slim`, сначала
`requirements.txt` + `pip install`, потом остальной код — ради кэша
слоёв сборки), `.dockerignore` (исключает `.env`, `.git`, `russian_memes.db`
из образа), `docker-compose.yml` (секреты — через `env_file`, БД — через
`volume`, не копированием, чтобы не терять данные при пересборке;
`restart: unless-stopped`). Собрано и запущено локально через
`docker compose up --build` — контейнер стабильно работает, бот отвечает
в Telegram через прод-токен.

**Обнаружено при тестировании через Docker:** старые approved-мемы в БД
были загружены через отдельного тестового бота (другой `BOT_TOKEN`).
`file_id` жёстко привязан к конкретному боту (см. "Почему один бот, а не
два" выше) — при попытке отправить такой `file_id` через прод-бота
Telegram возвращал `400: wrong file identifier`. Не баг кода — ограничение
платформы. Решение: очищена вся таблица `russian_memes` (`DELETE FROM
russian_memes`, было 55 мёртвых записей от тестового бота), дальнейшее
тестирование — только через прод-бота.

**Обнаружено в `.env` при ревью:** помимо трёх нужных переменных
(`BOT_TOKEN`, `MODERATOR_ID`, `API_URL` — последняя добавлена для
проксирования запросов к Telegram Bot API, без подписи `KEY=`) была
случайно оставленная лишняя строка со значением, похожим на токен
другого бота (не мешает работе — `python-dotenv` её просто
игнорирует как невалидную запись, но стоит убрать/разобраться, что это).

## Дальнейшие шаги (после базового MVP, не сейчас)

- буферизация альбомов (`media_group_id`) в `sendMeme`, чтобы не слать
  по подтверждению на каждое фото альбома — см. "Известное и осознанно
  принятое ограничение" выше
- избыточный `else` после `if ...: return` в трёх хендлерах
  `handlers_moderation.py` (`getAllMemes`, `reject_memes`, `approve_all`)
  — не баг, но лишняя вложенность, стоит почистить заодно с другими
  мелкими правками
- хрупкость параметров в `reject_memes_by_ids` (`db.py`) — `(ids)` без
  запятой работает только потому, что `ids` уже список; стоит явно
  прокомментировать или обернуть для ясности (в отличие от
  `count_user_memes_today`, где такая же по виду конструкция была бы
  реальным багом)
- разобраться с лишней/непонятной строкой в `.env` (см. выше)
- CI/CD (например, GitHub Actions) — обсуждали, решили отложить: сначала
  нужен реальный сервер и стабильный ручной деплой, автоматизация имеет
  смысл при частых деплоях или работе в команде — пока не тот случай
- дедупликация не только по точному `file_id`, но и по perceptual hash
  (ловит пережатые копии; актуально, когда разные юзеры независимо
  заливают один и тот же мем — у них будет разный `file_id`, точное
  сравнение строк это не поймает)
- лимит на количество pending-мемов от одного юзера в день
- `reject_memes_by_ids` не проверяет `cursor.rowcount` — если модератор
  укажет несуществующий id, бот всё равно отрапортует, что он "отклонён"
- вынос логики работы с БД в отдельный API-сервис
- выбор хостинга и переход с SQLite на что-то серверное (Postgres),
  когда появится реальный трафик
- почистить неиспользуемую колонку `photo_path` из схемы
- `reject_memes_by_ids` не проверяет `cursor.rowcount` — если модератор
  укажет несуществующий/уже обработанный id, бот всё равно отрапортует,
  что он "отклонён". Реальный риск на практике низкий (модератор — я сам,
  id вижу перед глазами через `/pending`), но не нулевой — можно
  опечататься при ручном наборе номеров. Оставлено в бэклоге осознанно,
  не как критичный баг: цена ошибки — только я сам, введённый в
  заблуждение собственным ботом, а не сторонний пользователь. Почистить
  вместе с другими мелкими задачами, не в приоритете.

### Массовая модерация (batch review) — реализовано

Проблема: MVP изначально модерировал по одному мему за раз (кнопки ✅/❌
под каждым сообщением через `/pending`). При росте потока (сотни
pending-мемов) это неудобно — либо скроллить десятки сообщений, либо
кликать кнопку под каждым по отдельности.

Рассматривали два подхода:

- **(Б) Пост-модерация** — одна команда `/approve_all` сразу
  одобряет все pending без предварительного просмотра, чистка плохого
  контента — постфактум, по мере обнаружения. Самый быстрый по
  количеству действий, но есть окно, когда неуместный контент уже
  виден пользователям.
- **(А) Пре-модерация без кнопок под каждым мемом** — выбранный
  подход. Бот присылает все pending-мемы на просмотр (каждый с
  подписью-номером = `id` записи), модератор их просматривает без
  клика по каждому. Если что-то не подходит — одной командой
  `/reject <id1> <id2> ...` отклоняет конкретные. Бот подтверждает
  результат ("отклонены: ..., осталось на рассмотрении: N") — защита
  от опечатки в id. После этого одной командой `/approve_all`
  (`UPDATE status='approved' WHERE status='pending'`) одобряется
  всё оставшееся — уже отклонённые записи не попадут под это условие,
  даже если бы команды были вызваны в другом порядке.

Выбор в пользу (А): при росте проекта есть риск, что через сервис
пройдёт неуместный/незаконный контент, за который модератор/владелец
может нести ответственность. (Б) экономит чуть больше времени, но
допускает временную публикацию до просмотра — цена ошибки выше
экономии. Решили подстраховаться заранее, раз это дёшево сделать
сейчас.

Ограничение платформы: Telegram Bot API не позволяет прикреплять
inline-кнопки к альбому (`send_media_group`) — группировка нескольких
фото с одной общей кнопкой технически недоступна.

## Важное по безопасности

Токен бота — как пароль, никогда не хранить в коде "как есть" и не
светить в чатах/репозиториях. Хранить в переменной окружения или
`.env`-файле, добавленном в `.gitignore`. Если токен уже засветился —
перевыпустить через @BotFather (Bot Settings → API Token → Revoke
current token).

`MODERATOR_ID` (личный `telegram_id`) тоже хранится в `.env` — не потому,
что это секрет в том же смысле, что токен, а чтобы не хардкодить магическое
число прямо в коде и не светить его в репозитории без необходимости.

Версии зависимостей в `requirements.txt` зафиксированы (`==`), а не
оставлены "на последнюю версию" — чтобы случайное обновление библиотеки
(например, `pyTelegramBotAPI`) на новой машине не сломало код неожиданным
изменением API.
